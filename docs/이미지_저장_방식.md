# 🖼 이미지(사진) 저장 방식 정리

> 작성일: 2026-06-10 · 중고거래 플랫폼(jsp-web-project) 매물 사진 업로드 설계 논의 정리
> 결론 한 줄: **DB에는 "경로(문자열)"만 저장하고, 실제 사진 파일은 외부 스토리지에 둔다.**

---

## 1. 핵심 결론

| | 저장 대상 | 통상적인가? |
|---|---|---|
| **DB에 경로(URL)만** | `https://.../abc.jpg` 같은 문자열 | ✅ **표준** |
| DB에 사진 바이너리(BYTEA/BLOB) | 사진 자체 | ❌ 실무에선 거의 안 씀 |
| Redis | 사진 자체 | ❌ 부적합 (캐시 전용) |

> ⚠️ "DB에 저장"이 헷갈리는 이유: 두 가지 뜻이 있음.
> ① **경로만** DB에 = 표준 / ② **사진 바이너리를** DB에 = 실무 X.
> 둘 다 "DB"라는 단어를 써서 충돌처럼 보이지만, 통상적인 건 ①뿐이다.

---

## 2. 저장소별 비교

### Redis → ❌ 사진 저장에 부적합
- 메모리(RAM) 기반 **캐시**. 이 프로젝트에선 "인기 랭킹"처럼 작고 자주 읽는 데이터에만 사용.
- 사진(수십 KB~수 MB)을 넣으면 서버 메모리를 잡아먹고, 메모리 부족 시 **삭제(eviction)** 되어 유실됨.
- → 사진 원본은 Redis에 저장하지 않는다. (Redis는 랭킹 용도 유지)

### DB → 두 방식
- **(a) 경로만 저장 (권장·표준)**: 파일은 디스크/스토리지, DB엔 경로 문자열만. `product_images` 테이블이 이 구조를 의도한 설계(상품 1개에 사진 여러 장).
- **(b) 바이너리 저장 (BYTEA/BLOB)**: 사진 자체를 DB에. DB가 비대해지고 느려지며 백업·복제 비용 폭증 → 실무에선 회피.

### 파일시스템 → ✅ 흔함
- 파일은 폴더에, 경로는 DB에. 위 2-(a)와 같은 얘기.

---

## 3. 실서비스(당근마켓·쿠팡·인스타 등)의 실제 구조

```
[사용자] --업로드--> [앱 서버] --파일 전송--> [오브젝트 스토리지]
                                              (AWS S3, GCS, 네이버 NCP 등)
                                                    │
[DB] ← 이미지 URL/키 문자열만 저장 ─────────────────┘
                                                    │
[사용자] <--표시-- [CDN] <--원본 캐싱--────────────┘
```

1. **원본 파일** → S3 등 오브젝트 스토리지(외부 서버)에 저장
2. **DB** → 파일이 아니라 그 **URL/키 문자열만** 저장
3. **표시** → CDN을 거쳐 빠르게 전송

| 방식 | 실서비스 채택 | 이유 |
|---|---|---|
| **오브젝트 스토리지 + DB에 URL + CDN** | ✅ 표준 | 무한 확장, 서버 부담 0, CDN 캐싱 |
| DB 바이너리(BYTEA) | ❌ | DB 비대·저속, 백업 비용 ↑ |
| 앱 서버 로컬 폴더 | ❌ | 서버 스케일아웃 시 공유 불가, 서버 유실 시 유실 |
| Redis | ❌ | 메모리 캐시, 영구저장 아님 |

핵심 이유:
- **스케일아웃**: 서버를 여러 대로 늘릴 때 파일을 외부로 분리해야 서버가 상태 없이 자유롭게 늘어남.
- **역할 분리**: DB(비싼 검색 자원)에 큰 파일을 넣는 건 낭비. 스토리지(싼 보관 자원)에 맡긴다.
- 추가로 실서비스는 썸네일 자동 생성·이미지 최적화(webp)·업로드 검증(용량/확장자/악성코드)까지 처리.

---

## 4. 이 프로젝트에 적용할 방향

학교/로컬 프로젝트엔 S3·CDN이 과하므로, **실무 원리를 그대로 축소**한다:

> **로컬 폴더 = "오브젝트 스토리지" 역할**, **DB(`product_images`)엔 경로만 저장**

→ 실서비스 아키텍처(원본은 스토리지, DB엔 경로만)를 충실히 흉내 낸 미니 버전.
발표 시 "원본은 스토리지, DB엔 경로만 — 실서비스도 이렇게 합니다"로 설명 가능.

### 구현 완료 (2026-06-10)

실서비스 구조의 축소판 — **파일은 외부 폴더, DB엔 경로(`/images/{파일명}`)만** — 으로 대표 사진 1장 업로드를 구현했다.

**동작 흐름**
```
[등록 폼] --multipart--> [ProductController.savePhoto()] --파일 저장--> [외부 폴더 upload.dir]
                                    │                                   (C:/Users/ssant/upload)
                          DB products.thumbnail 에 "/images/{uuid}.jpg" 문자열만 저장
                                    │
[목록/상세 <img>] --GET /images/{uuid}.jpg--> [ImageController] --폴더에서 읽어 스트리밍-->
```

### 다중 이미지 (여러 장) 지원

대표 사진 1장에서 **여러 장 업로드**로 확장. `product_images` 테이블 활용.

- **저장 전략**: 첫 장 = 대표 사진(`products.thumbnail`, 목록 그리드용) / 전체 = `product_images`(상세 갤러리용). 대표를 따로 둬서 목록 조회는 가볍게 유지.
- **목록(main.jsp)**: 기존대로 `thumbnail` 1장만 표시
- **상세(detail.jsp)**: `product_images` 전체를 **좌우 스와이프 갤러리**(scroll-snap)로 표시, 없으면 thumbnail/picsum 폴백

**변경 파일**
1. `db.properties` (+example): `upload.dir=C:/Users/ssant/upload` 추가 (저장 폴더, 앱 바깥이라 재배포에도 사진 유지)
2. `global/web/ImageController.java` (신규): `@WebServlet("/images/*")` — 외부 폴더의 파일을 읽어 서빙. `../` 경로 조작 방어 포함. LoginCheckFilter 보호 대상 아님(누구나 조회 가능)
3. `product/ProductController.java`: `@MultipartConfig`(파일 10MB·요청 50MB 제한) + `savePhotos()` — `req.getParts()`의 `photos` 파트들을 UUID 파일명으로 저장 후 `/images/{파일명}` **목록** 반환
4. `product/ProductDAO.java`: `insert()`가 생성 id 반환(RETURN_GENERATED_KEYS) + `insertImages(productId, urls)`(배치) + `findImageUrls(productId)` 추가
5. `product/ProductService.java`: `write(userId, product, imageUrls)` — 첫 장을 thumbnail로, 전체를 product_images에 저장 / `getProductDetail()`에서 이미지 목록 로드
6. `product/ProductDTO.java`: `List<String> images` 필드 추가(상세 갤러리용)
7. `views/product/form.jsp`: `enctype="multipart/form-data"` + `<input type="file" name="photos" accept="image/*" multiple>`(라벨로 감쌈) + 다중 미리보기 JS(첫 장 주황 테두리=대표)
8. `views/product/main.jsp`·`detail.jsp`: `<img>` src에서 업로드 경로(`/`로 시작)면 contextPath를 붙이고, 외부 URL(`http`)이면 그대로, 미첨부면 picsum 임시 이미지. detail은 다중 갤러리 렌더링

**남은 개선 (선택)**
- 검증 실패로 폼 되돌아갈 때 이미 저장된 파일이 고아로 남음(무해) — 정리 로직 추가 여지
- 상품 수정 폼에서 기존 사진 교체/삭제 UI (백엔드는 새 사진 업로드 시 대표만 교체)
- 썸네일 리사이즈/webp 변환/확장자 화이트리스트 검증(실서비스가 하는 것)
